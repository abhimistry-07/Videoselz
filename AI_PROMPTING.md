# AI Prompting Log

This log records significant AI-assisted interactions during development, per the assessment's AI Collaboration requirements. Tool used throughout: Claude (Anthropic).

_Note: some prompts below are lightly reconstructed from a longer iterative conversation for clarity — the substance, actual code produced, and decisions made are accurate to what was actually built._

---

## 1. TypeORM + SQLite Configuration

**Tool Used:** Claude

**Context/Task:** Setting up the initial NestJS + TypeORM + better-sqlite3 connection in `app.module.ts`.

**Exact Prompt Used:** "Is this correct?" — followed by the pasted `app.module.ts` file containing the TypeORM configuration.

**Outcome & Adjustments:** AI caught a package mismatch — I had configured `type: 'better-sqlite3'` but had actually installed the `sqlite3` package instead, which would have failed at runtime. Installed `better-sqlite3` to match. Also adopted DI-based `ConfigService` injection over raw `process.env` access for better testability, per the AI's suggestion.

## 2. Database Schema Design (Entities & Relations)

**Tool Used:** Claude

**Context/Task:** Defining Product, Video, and EngagementEvent TypeORM entities matching the spec's normalized schema (Products: ID, Name, Price, CreatedAt; Videos: ID, ProductID, VideoURL, Title; EngagementEvents: ID, VideoID, EventType, Timestamp).

**Exact Prompt Used:** "Then why in products we are mentioning videoId?" — questioning why the generated `Product` entity included a `videos: Video[]` property when the spec's Products schema has no video reference.

**Outcome & Adjustments:** AI clarified the distinction between a real DB foreign key column (which only exists on the `Video` table via `@ManyToOne`) versus an ORM-level inverse relation property (`@OneToMany` on `Product`, which adds no column to the database). Verified this against the actual generated migration SQL to confirm no extra column was created on the `products` table.

## 3. Rejected AI Suggestion: @RelationId Pattern

**Tool Used:** Claude (reviewing a suggestion originally generated by a different AI tool)

**Context/Task:** A separate AI suggested refactoring the `Video` entity's `productId` field to use TypeORM's `@RelationId` decorator instead of an explicit `@Column`, claiming the current setup created two independently-mapped columns and risked inconsistency.

**Exact Prompt Used:** "Do I have to do this or not needed?" — pasted alongside the other tool's suggested `@RelationId` refactor.

**Outcome & Adjustments:** Asked Claude to verify the claim against the actual generated migration SQL. The migration showed only **one** `product_id` column existed — disproving the premise of the suggestion. Rejected it and kept the explicit `@Column` + `@ManyToOne` pattern, which is more appropriate here since `ProductID`/`VideoID` are required, validated fields per the spec rather than optional lazily-computed values. Logged as an example of catching an incorrect AI suggestion by verifying against real output rather than trusting the stated reasoning.

## 4. Seed Script Cleanup Order

**Tool Used:** Claude (reviewing a suggestion originally raised by a different AI tool)

**Context/Task:** A suggestion claimed the seed script's table-cleanup order (products → videos → events, matching insertion order) would cause a foreign-key constraint failure, and that cleanup should happen in reverse dependency order instead.

**Exact Prompt Used:** "You're deleting in the wrong dependency direction... Instead, seed cleanup should happen in reverse dependency order... Do I have to do this or not needed?"

**Outcome & Adjustments:** Verified that the claimed failure wouldn't actually occur, since all relations use `onDelete: 'CASCADE'`, meaning SQLite already cascades deletes automatically. However, agreed the suggested restructure (explicit reverse-order deletes centralized in `index.ts`, not relying on cascade side-effects) was still a genuine improvement for explicitness and robustness, even though the original justification was inaccurate. Adopted the restructure for the right reason.

## 5. Analytics Aggregation Query (Avoiding Cartesian Product)

**Tool Used:** Claude

**Context/Task:** Building the `GET /api/analytics/videos` endpoint — the assessment brief explicitly warns that this must support pagination and avoid returning duplicated/inflated rows from bad JOINs.

**Exact Prompt Used:** "Build the analytics service for GET /api/analytics/videos. It needs to return each video with total views, clicks, and add_to_cart counts aggregated from the engagement_events table, with pagination. The assessment brief specifically warns about cartesian product bugs from bad JOINs — make sure this avoids that."

**Outcome & Adjustments:** AI used a single `LEFT JOIN` with conditional aggregation (`SUM(CASE WHEN event.eventType = 'x' THEN 1 ELSE 0 END)`) instead of multiple JOINs or separate per-type COUNT queries, avoiding row multiplication entirely in one pass. Verified correctness by cross-checking the returned totals against the seed script's console-logged counts — numbers matched exactly.

## 7. Next.js Client/Server Component Boundary

**Tool Used:** Claude

**Context/Task:** Fetching analytics data into the dashboard page and rendering loading/error states.

**Exact Prompt Used:** "I need to fetch analytics data from my NestJS backend into the Next.js dashboard page on load, store it in state, and handle loading and error states. Show me how to set this up."

**Outcome & Adjustments:** Learned the distinction between Server and Client Components in the App Router — `'use client'` is required at the top of `page.tsx` since `useState`/`useEffect` and browser `fetch` aren't available in Server Components by default. Structured `fetchData` as a named, reusable function rather than inlining it in `useEffect`, anticipating it would need to be re-triggered later by the Simulate Traffic button.

## 10. Simulate Traffic Button & GET /api/videos Endpoint

**Tool Used:** Claude

**Context/Task:** Building the "Simulate Traffic" button, which needed a valid, real `videoId` to POST against.

**Exact Prompt Used:** "The Simulate Traffic button needs a real videoId to send. Should I hardcode the seeded video IDs on the frontend, or add a proper endpoint to fetch them?"

**Outcome & Adjustments:** Chose to add a minimal `GET /api/videos` (list-only, no create/update/delete) rather than hardcoding IDs on the frontend, since hardcoding would silently break if the database were ever reseeded differently. Then built the button to fetch the video list, pick one at random, generate a weighted-random event type (more views than clicks than conversions, mirroring the seed script's funnel logic), POST it, and trigger a table refresh via a callback prop.

## 11. Pagination Controls

**Tool Used:** Claude

**Context/Task:** Adding Previous/Next pagination to the dashboard table, wired to the backend's `page`/`limit` query params.

**Exact Prompt Used:** "Add pagination to the dashboard — Previous/Next controls that call the analytics endpoint with page and limit params, disabling buttons at the first/last page."

**Outcome & Adjustments:** Built a controlled `Pagination` component that holds no state itself, receiving `page`/`limit`/`total` as props and calling an `onPageChange` callback — keeping the state ownership in the parent page component, which also owns the data-fetching logic.
